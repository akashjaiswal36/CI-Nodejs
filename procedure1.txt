📁 STEP 4C — Add GitHub Actions Workflow

Create this file in your app repo:

ci.yaml file:

name: CI - Build & Push Docker Image

on:
  push:
    branches:
      - main

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
    - name: Checkout code
      uses: actions/checkout@v4

    - name: Set up Docker Buildx
      uses: docker/setup-buildx-action@v3

    - name: Login to Docker Hub
      uses: docker/login-action@v3
      with:
        username: ${{ secrets.DOCKERHUB_USERNAME }}
        password: ${{ secrets.DOCKERHUB_TOKEN }}

    - name: Build and push Docker image
      uses: docker/build-push-action@v5
      with:
        context: .
        push: true
        tags: |
          ${{ secrets.DOCKERHUB_USERNAME }}/devops-demo:latest
          ${{ secrets.DOCKERHUB_USERNAME }}/devops-demo:${{ github.sha }}

1️⃣ Canary deployments (Argo Rollouts)

1️⃣ What is Canary Deployment (in real words)

Instead of deploying a new version to 100% users, you:

Deploy to small % first

Observe metrics

Gradually increase traffic

Roll back automatically if things break

Example:
v1 → 100% traffic
v2 → 10% → 30% → 60% → 100%


If error rate spikes at 30% → rollback automatically

📄 helm/devops-demo/templates/rollout.yaml

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: {{ include "devops-demo.fullname" . }}
spec:
  replicas: {{ .Values.replicaCount }}
  revisionHistoryLimit: 2

  selector:
    matchLabels:
      app: {{ include "devops-demo.name" . }}

  template:
    metadata:
      labels:
        app: {{ include "devops-demo.name" . }}
    spec:
      containers:
      - name: app
        image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
        imagePullPolicy: {{ .Values.image.pullPolicy }}
        ports:
        - containerPort: 3000
        env:
        - name: APP_VERSION
          value: "{{ .Values.env.APP_VERSION }}"

  strategy:
    canary:
      steps:
      - setWeight: 10
      - pause: { duration: 30s }
      - setWeight: 30
      - pause: { duration: 30s }
      - setWeight: 60
      - pause: { duration: 30s }
      - setWeight: 100
-------------------------------------------

30% → pause

2️⃣ Default EKS behavior (THIS IS WHY IT WORKS AUTOMATICALLY)

When you create an EKS cluster using eksctl or AWS console:

✅ AWS automatically attaches this policy to worker nodes:
AmazonEC2ContainerRegistryReadOnly

That policy allows:

ecr:GetAuthorizationToken

ecr:BatchGetImage

ecr:GetDownloadUrlForLayer

📌 Result
Your pods can pull images from ECR without any Kubernetes secret.

That’s why you did not configure docker-registry secrets.

3️⃣ Then WHAT is IRSA? (important distinction)

IRSA = IAM Roles for Service Accounts

IRSA is NOT needed for image pulling.

IRSA is needed when:

Pods need to access AWS APIs at runtime

Examples:

S3

Secrets Manager

DynamoDB

SQS

📌 Image pull = node responsibility
📌 AWS API calls = pod responsibility

5️⃣ IRSA — Step-by-step (REAL IMPLEMENTATION)

We’ll do a real IRSA example (Secrets Manager access).

STEP 5.1 — Enable OIDC provider for EKS

Run once per cluster:

eksctl utils associate-iam-oidc-provider \
  --cluster devops-demo-cluster \
  --region ap-south-1 \
  --approve


This allows:
“Kubernetes service accounts → IAM roles”

STEP 5.2 — Create IAM Policy (example: Secrets Manager)

Create file secrets-policy.json:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "secretsmanager:GetSecretValue"
      ],
      "Resource": "*"
    }
  ]
}

----------------------------
Create policy:

aws iam create-policy \
  --policy-name devops-demo-secrets-policy \
  --policy-document file://secrets-policy.json

  ------------------------------------------------
  STEP 5.3 — Create IAM Role bound to ServiceAccount (IRSA)
eksctl create iamserviceaccount \
  --cluster devops-demo-cluster \
  --namespace default \
  --name devops-demo-sa \
  --attach-policy-arn arn:aws:iam::<ACCOUNT_ID>:policy/devops-demo-secrets-policy \
  --approve


This creates:

IAM role

Trust policy with OIDC

Kubernetes ServiceAccount

Annotation linking both

---------------------------

STEP 5.4 — Use ServiceAccount in your Rollout / Deployment

In your rollout.yaml:

spec:
  template:
    spec:
      serviceAccountName: devops-demo-sa
      containers:
      - name: app
        image: <ECR_IMAGE>


That’s it.

Exec into pod:

kubectl exec -it <pod-name> -- sh


Run:

aws sts get-caller-identity


You should see:

AssumedRole/devops-demo-sa
